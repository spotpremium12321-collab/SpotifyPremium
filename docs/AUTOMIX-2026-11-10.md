# AutoMix, not working: the chain and where it can die (2026-11-10)

Reported as "automix isnt working". The code is in `Shared/AutoMix/` (model, runtime, hooks, settings)
and the pill that shows a mix window is `Redesigned/Player/PlayerMixing.x`. The policy is sound: both
harnesses pass (below). So the failure is in one of the links between the mod and Spotify's playback,
and each link has a signature you can read off the phone in a minute. This is what was checked and
what to look at.

## What "working" means

Two mechanisms, one switch (`spotifyglass.automix`, Mod Settings → AutoMix, off by default):

- **Spotify's plan.** Smart blend asks Spotify for a transition on the context it is playing
  (`automix.mode=regular` and friends added to the play request). Where the backend supplies a plan,
  the track's metadata carries `automix.transition_uri` and fade times, and Spotify's own beat-matched
  AutoMix plays it. The mod turns Spotify's automix preference on and its crossfade off for that track.
- **Crossfade fallback.** Where no plan comes back (most tracks), the mod turns crossfade on with the
  configured length, written into Spotify's playback preferences.

So "nothing happens" and "it only crossfades, never beat-matches" are different failures: the first is a
dead link, the second is usually the backend declining a plan.

## The chain, and the gate on each link

1. **The switch is read at launch.** `SGAutoMixEnabled()` in the `%ctor` (`AutoMix.x`), which then forces
   `ios-feature-settings.automix_enabled` / `crossfade_enabled` and registers the player/preferences
   hooks. Off at launch (or no restart after toggling) = the rest of the chain does not exist.
2. **Spotify's config has automix and crossfade enabled.** `SGAutoMixConfiguration` patches
   `core-automix.automix_enabled` and `core-playback-setup.crossfade_enabled` to 1 as the config arrives;
   `Premium.m`'s rules force the same two (and the UI flags) regardless, when Spoof Premium is on.
3. **The play request asks for a transition.** `SGAutoMixCopyContext` copies the context and sets
   `automix.mode=regular`, `automix.ignore_setting=true`, `automix.queue`, `automix.autoplay` when the
   context is one of the ticked kinds (playlist, album, Liked Songs, artist/radio). Needs the context to
   be `NSCopying` and to have `metadata`/`setMetadata:`.
4. **The backend answers with a plan, or does not.** Nothing in the client controls this. A plan puts
   `automix.transition_uri` / `audio.fade_out_*` into the track's metadata, which is what
   `SGAutoMixHasTransition` reads.
5. **The policy writes Spotify's preferences** (`AutoMixRuntime.m`, `apply()`): plan → automix on,
   crossfade off, time 0; otherwise → automix on for Smart blend, crossfade on at the configured length
   in milliseconds. Needs the preferences object, which is captured from the getters
   `audioAutomix` / `audioCrossfade` / `audioCrossfadeTime` when Spotify reads them.
6. **Spotify's playback honours those preferences.** The crossfade switch and length are read by the
   fade engine (that is what `Shared/AdBlock/Crossfade.x` exists for: the length slider writes only the
   length). If the app has moved crossfade to the playback-settings store, the legacy preference the
   mod writes may no longer be what playback reads (see below).

## Verified in this pass

Against the 9.1.90 binary (`ipa/com.spotify.client_9.1.90_und3fined.ipa`), everything the code names
exists: `_TtC31Preferences_CorePreferencesImpl28SPTPreferencesImplementation` with `audioAutomix`,
`audioCrossfade`, `audioCrossfadeTime` and their setters; `SPTEsperantoPlayer` with the five play
selectors it hooks and `addPlayerObserver:`; `ESPContextPlayerClientImpl`; `SPTRemoteConfigCoreImpl`;
`initWithScheduler:`; the metadata keys `automix.mode`, `automix.ignore_setting`, `automix.queue`,
`automix.autoplay`, `automix.transition_uri`, `audio.fade_out_duration`, `audio.fade_out_start_time`,
`audio.fade_overlap`, `media.stop_position`; the config scopes `core-automix.automix_enabled` and
`core-playback-setup.crossfade_enabled`; and the values `regular`, `airbag`, `radio_airbag`, `sleep`,
`mixed`, `custom`, `heuristic` for `automix.mode` — so `regular` is a real request, not a guess. The
playback-settings proto field is `crossfade_duration_ms`, so milliseconds is the right unit for the
crossfade length.

Offline: `sh harness/automix/build.sh` and `sh harness/automix/hooks-build.sh` both PASS — context
selection, copy semantics, metadata preservation, core flags, the millisecond length, no repeated
writes, plan/fallback selection, restoration including deliberate user edits, and discovery of the
preferences object without `initWithScheduler:` (through normal reads, and through a replacement
object's setter). The harnesses do not run Spotify's audio engine, do not fetch plans, and feed the
state in directly, so they cannot show a dead link in steps 3–6 on the phone.

## Where it can die, in the order worth checking

1. **Not restarted / switch off.** Status: `Off · Spotify's playback settings`.
2. **The context is not one of the ticked kinds.** Status: `Spotify's settings · outside selected music
   contexts`. Single tracks, search playback, podcasts and local files are never eligible.
3. **The preferences object was never captured.** Status: `Waiting for Spotify's playback preferences`.
   This is the likeliest silence on 9.1.90: the capture depends on Spotify reading the legacy getters,
   and 9.1.90 also carries `audio.crossfade_migrated_to_ps`,
   `playback-settings.use_playback_settings_crossfade` and a playback-settings storage proto — if this
   build reads crossfade from that store, Spotify never touches the getters the mod watches, and the
   fallback is never written (nor would writing it be heard).
4. **No plan from the backend.** Status: `Next transition · N s crossfade (no Spotify plan)`, which is
   correct behaviour — the sound then depends on link 6, i.e. on 3.
5. **The preferences are written but playback ignores them.** Status shows `Next transition · …` while
   nothing is heard: the legacy-preference path is dead on this build (same suspicion as 3, seen from the
   other side), or the fade engine caches the switch at the start of playback.

## The five checks (about two minutes)

1. Mod Settings → AutoMix: is the switch on, and what does **Current playback** say? That one line names
   links 1–4 already.
2. Play a music playlist, then open **Transition details**: does `automix.mode` appear under "Transition
   metadata:? If it does, the request went out and the backend answered; if it does not, either the
   request never went (check 4) or the backend sent no plan for this song.
3. `make log` while starting that playlist, with AutoMix on, and look for:
   - `automix: <context> asked for a transition` (or a `cannot ask for a transition, …` line naming why) —
     link 3;
   - `automix: captured playback preferences from <class>` — link 5's object;
   - `automix: Next transition · …` — the policy's decision.
4. With AutoMix **off**, set Spotify's own crossfade (Settings → Playback → Crossfade) to 12 s and play a
   playlist. If tracks crossfade, the preference path playback reads is alive and link 6 is fine; if they
   do not, the crossfade has moved to a store the mod does not write, and no fallback can work until it
   does.
5. In the redesigned player, near the end of a song that has a next one queued, the mix pill should come
   up (`SGAutoMixMixWindow`). No pill means the window itself is not being built (context not eligible, or
   no queued next song).

## What this pass changed

`SGAutoMixCopyContext` / `SGAutoMixCopyRequest` now log the request side once per context and reason
(`automix: <uri> asked for a transition`, or `cannot ask for a transition, <why>`), which nothing
reported before — the existing logs only cover the policy's decision and the preferences capture. This
is diagnosis, not a fix: nothing in the policy was wrong to fix.

What a fix would be, by answer:

- Never asked, or the request cannot carry the context → the copy/metadata path needs the real
  `SPTPlayerContext` shape (a runtime dump, `trees/`-style, answers that).
- Asked, no plan → the backend declines; the crossfade fallback is the only lever, so the work is on
  link 6.
- No preferences captured, or written and not heard → read/write the playback-settings store the build
  actually uses, or find the preferences object another way; both need a dump of
  `SPTAudioPlayback_PropertiesImpl` / the preferences instance from the phone first.

## Device result 1 (2026-11-10, later)

AutoMix **off**, Spotify's own crossfade at 12 s: tracks still play one after another, no overlap. So the
crossfade itself is dead on this build — upstream of AutoMix. The switch, eligibility, the request side and
the policy are all irrelevant to that symptom, and AutoMix's fallback could never have sounded.

That moves the suspect list onto the crossfade gate. The mod had forced
`ios-feature-settings.use_playback_settings_crossfade` to **NO**, under a note that says the
ios-feature-settings flags only draw the rows. 9.1.90 also carries a `playback-settings` scope with the
*same* name, and a playback-settings store with `enable_crossfade` and `crossfade_duration_ms` — a core that
reads either copy suppresses exactly the preference the slider writes. The rule is now YES in both scopes
(`Premium.m`), and the AutoMix page grew a **Spotify's config** row that reads the crossfade, automix and
gapless lines out of `Caches/spoti.pw/AdBlock/live-config.txt`, which is written before the mod patches
anything: the server's own gate value, readable on the phone.

Next: with AutoMix off, set Spotify's crossfade to 12 s and play a playlist again.

- If it crossfades now, that rule was the break, and AutoMix's crossfade fallback follows it.
- If it does not, read **Spotify's config** on that page. A `playback-settings.use_playback_settings_crossfade
  = false` there means the server gates it; if the core ignores the mod's force, the next step is the store's
  own `enable_crossfade` in `SPTAudioPlayback_PropertiesImpl`, which needs a runtime dump from the phone
  first (the mod reads Swift properties that way in `SGRDownload`).

## Storage-selection fix (2026-11-10, subsequent pass)

The preceding YES/YES change selects the new playback-settings store, but AutoMix's
runtime only writes `audioAutomix`, `audioCrossfade` and `audioCrossfadeTime` on the
legacy preferences object. Passing the existing harness did not establish that the
playback engine was reading those writes. The earlier claim that there was nothing
in the integration to fix was too strong.

AutoMix now forces **both** `ios-feature-settings.use_playback_settings_crossfade`
and `playback-settings.use_playback_settings_crossfade` to false while its launch
hooks are active. The crossfade/AutoMix enable flags remain true. One shared map
supplies the Objective-C configuration-provider overrides and the serialized core
configuration patch, including flags missing from the server's response. This is
independent of Spoof Premium; the core patch runs as the configuration is handed to
`SPTRemoteConfigCoreImpl`, after the network Premium rewrite. With AutoMix off at
launch these overrides are absent. No new Spotify selector or binary patch was added.

Static evidence from the bundled 9.1.90 executable, SHA-256
`57bd5a9bc60bf4304f3043df3d32d50d3b095222719cd54e9805ad1ccef7c381`:

- `SPTAudioPlayback_PropertiesImplProperties`'s `initWithConfigurationProvider:`
  (Objective-C entry `0x107ebc844`, Swift body `0x1070035c8`) reads
  `ios-feature-settings.use_playback_settings_crossfade` (string `0x10a6077f0`)
  and stores its boolean in `usePlaybackSettingsCrossfade` at instance offset 12.
- The core config accessor `0x10790b234` uses scope `playback-settings` and property
  `use_playback_settings_crossfade` (`0x10a3ad5f0` / `0x10a3ad602`).
- The migration code at `0x1099af1fc` checks its crossfade gate and
  `audio.crossfade_migrated_to_ps`, then reads the old crossfade switch/duration and
  conditionally copies them into device-setting fields 10 and 11. This is a guarded
  migration, not a continuous bridge from AutoMix's writes to that store.
- The legacy Objective-C getters/setters exist with boolean and NSInteger types;
  the duration setter is `0x10575c274`, getter `0x1021528f0`.

These observations used local `otool` metadata and Capstone disassembly. REA's
native provider was unavailable and its standalone Mach-O inspection timed out;
these are not REA Evidence records. Static evidence establishes the two stores and
configuration mismatch, not audible playback on the phone.

The added regression failed before the fix (`Absent storage gates select the legacy
preferences AutoMix writes`) and passes afterward under ASan/UBSan. It covers both
absent and true storage gates, preservation of other flags in the same scope, and
idempotence. The simulator harness verifies that the production Logos constructor
registers both false overrides ahead of manual flag overrides and keeps the fade
engine enabled. Existing preference capture/restoration and transition tests pass.

Phone verification remains required: install, enable AutoMix and restart, choose
Crossfade at 12 seconds, start a music playlist on this iPhone, and use Preview next
transition. The next track should overlap the outgoing one. Then test Smart blend
and turn AutoMix off to check restoration. A predicted mix pill or a selected status
alone is not proof of audible overlap.
